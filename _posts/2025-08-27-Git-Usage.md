# Git真的会用了吗？

## git rebase 变基

使用Git进行版本管理的时候，你是否还在一直使用git add . git commit 以及git pull  git push 吗？如果您是一个项目的负责人，应该还会使用过git merge的操作。嗯，我们可能最怕的就是merge的时候，文件产生了冲突，每次解决都需要下定莫大的决心？

嗯。使用git merge，没问题，要是对系统进行发版，咋办？好处理啊，打一个tag的标签不就行了？但此时，有个问题不知道您考虑过没？就是如果我在打tag标签之前，就checkout了一个新的分支，并在master分支上有了新的提交，此时在最新的提交上打的tag，当master主分支合并了新分支后，此时的tag指向，还能保证就是当前的版本吗？

假设新分支为feature，commit是c，master分支上的commit为d，且c的提交要早于d，那么，merge后的commit的顺序就是 c ，d，且d的父节点就是c，因为c的时间要早于d。

怎么办？怎么办？如果可以把d提交虽然是稍后于c，但在master上commit顺序不要变就可以了。那么，我们就可以在feature分支上做rebase操作，即变基操作，我们的feature是从master主干（使用过SVN的同学，可能更习惯于用主干，而git的同学，可能习惯为分支）上进行分叉的，那么，master和feature是有一个共同的commit，我们暂且称之为a，我们可能在修复bug也好，开发新的功能也好，此时，master还有一个commit为d，那么，在feature上rebase master分支的时候，就是这样操作的，把master分支的a，d先进行排序，此后，把feature分支上所有的提交（commit）再一次做一次新的提交（注意，真的是新的提交，所有的commit的sha值都会变化），即如果feature上新的提交依次为b，c ， e等，那么，就会再d后面重新提交b为 $ b^1 $ , c的提交为$c^1$,e的提交为$e^1$,那么，此时的顺序就是  $a ， b , c^1 , d^1, e^1 $ 这样的顺序了，那么，此时，我们的tag还会出现错乱吗？

总结一下，所谓rebase，就是把从原有分叉的地方，把需要rebase的分支checkout后的所有提交作为新的head，再依次把feature上的所有的提交再依次给排序进来。举个不恰当的例子，比如排队，现在有两个队，都是要再窗口上办业务，但突然之间，一个窗口不办理了，此时，所有排队的用户，都会给另一个正在办理业务的队尾，为了公平，那么，不办理业务的这个队，从头依次排到另一个队的队尾，虽然您可能比队尾的人来的要早，等候的时间要长，但为了公平，您还是要排在队尾。

如果，您只关注提交，只关注谁先提交了那些数据，并修改了那些数据，您可以使用git merge，merge的时候，会按照时间来进行排序，但是，如果您要是一个功能一个功能的上线，虽然有一些功能的提交要非常早，但还是要把这个功能的提交都给排在前面，那么，此时，您需要的就是rebase。此时，rebase的功能，不仅可以用来避免打的tag出现了问题，还可以基于CI/CD来进行部署或者发版的情况下，此时，基于commit的id来发版，我们可以在产生问题的时候，及时回滚到上一次的commitid，如果提交的commit顺序产生了错乱，那么，回滚的时候，就不容易找到上一次正确发布的commit了。

### git merge的命令

说完了大家不太愿意使用git rebase，实际上，大家最多使用的是git merge这个命令，使用git merge是非常熟悉和习惯的，git merge主要是用来把两个不同分支的提交合并到一起，此时的合并，就是按照所有的提交顺序来进行排序的。虽然是按提交顺序来排序，但是，git merge会把把所有修改过的commit的文件进行对比和diff，当发现两个文件不能合并时，即，两个commit修改了同一文件的同一位置，就会触发冲突，就需要我们自己手动来解决冲突。

git merge虽然不会像git rebase一样修改git commit的id，但是，git merge有时会生成一个新的commit，尤其是当两个分支有冲突的时候，我们可以这样理解，每次的修改，都会有一个commit，我们通过merge把两个分支合并到一起，此时，由于有一些文件有冲突，那么，我们还是需要修改这些冲突的文件，也就是要解决这些冲突，而解决冲突，就需要修改文件，或者使用一个分支的提交来作为当前文件的，最终，这些文件修改后，需要重新把这些文件给纳入到版本管理的管理中来，也就是需要生成一个新的commit。

为什么我们平时的时候都是使用git merge哪？我们开发一个功能的时候，大多数的情况下，都是多人同时进行开发的，这个时候，大家都会提交到功能分支上去，如果每次使用git rebase的话，那么，我们每次都会让commit进行了变化，这个时候，大家都需要根据自己的版本和提交进行强制更新，会浪费非常多的时间，而使用git merge，则可以大家同时开发，都merge到一个分支上，虽然会产生一些无效的commit，或者是没有意义的commit，但这些都代表着每个文件的变更，可以根据时间线和历史来进行排查。也方便大家可以很方便的从服务器上拉下来代码，并进行自己的开发。
