这个话题我挺有发言权。我在仓储作业系统一线做了好几年研发，正好亲历了"手写代码 → vibe coding → agent 帮我写一大半"的全过程。

先给结论，免得你划走：**大学生完全不用因为"手搓代码变少"而焦虑。但你要警惕另一种能力在悄悄退化——那才是真正会要命的。**

我前段时间做了个小调研：一个软件研发人员的时间，其实根本没花在"写代码"上。下面用两个我亲身经历的事故，说清楚时间到底花哪了，以及为什么 agent 再强，也替不了那部分。

## 一、编码只占研发时间的零头，理解业务才是大头

前阵子产品提了个需求：把页面上某类数据从展示里去掉。

背景是，业务早先加过一个"内部平衡"的需求，不紧急，后来把生成这些数据的定时任务停了，页面展示就出了岔子。第一次沟通，只说了"页面数据展示有问题，把这块数据除掉"。产品大概了解下，转给研发，研发用 AI 三下五除二把数据移了。上线。

结果上游一推数据，一线又炸了：还是大量数据异常。

这次我拉着业务和一线仓储人员，对着页面和数据库一起查。真相是：**页面上那点展示数据只是个参考，真正驱动一线转运作业的是导出的 Excel——而那个导出功能，根本没人动过。** 页面"修好"了，活儿照样乱。

你看，这需求从提出到真正解决，编码可能就半小时；但"搞清楚业务到底要什么、数据流向哪、一线到底看哪个界面"花了好几天。写代码，是这里面最便宜的一步。

## 二、系统编码的卡点，九成在"理解旧系统和对接"，不在"写不出来"

再说排查问题。我们系统从来不是一座孤岛：上游有订单、财务、工厂、定时盘点；下游对接收、质检、报废；中间还要去中台拉商品/物料的属性。一个接口背后，可能调内部服务，也可能调外部 RPC，还可能顺手查了张表。

我排查过一次线上突发超时。先紧急重启，现象消失，就先放过了。直到又来一次，我才死磕日志：发现一条慢 SQL，执行条件居然是 `where 1 = 1`——这不就是全表扫描吗？去看生产库，这张表上亿行，全读进内存，JVM 疯狂 Full GC，调度到这台机器的请求全超时。

看源码才明白：MyBatis 那句 SQL 条件一堆，可当所有参数都为空时，条件就退化成了 `where 1 = 1`。

这类问题，AI 也能帮你写出这段 SQL。但它**不知道**"这个参数在某些业务场景下会整体为空"，**不知道**"循环调外部 RPC 会把自己拖死"，也**不知道**"参数为空时会不会扫全表"。这些边界，是业务和场景教给你的，不是代码教给你的。

## 三、所以 agent 越强，你反而越需要懂业务——这是我和很多"别焦虑"回答不一样的第三点

高赞回答大多在说"别焦虑，代码在贬值，上游能力在升值"。我完全同意。但我想补一个容易被忽略的点：

**agent 帮你写代码，会让你更快地踩到"你不懂业务"的坑。**

过去你手写代码，每一行都得自己想清楚，边界不清你根本写不下去，反而被迫去问业务。现在 agent 一键生成，代码跑起来了，你以为成了——可一旦业务场景稍微偏一点（比如参数整体为空），bug 就在生产环境等你。

手写时代，bug 暴露在你写代码的那一刻；agent 时代，bug 暴露在一线同事的工位上。

所以"丧失手搓能力"本身不可怕，**可怕的是连"这段代码在哪种业务下会出错"都不再过脑子。** 手搓是慢，但它逼你思考；agent 是快，但它替你思考——如果你不主动把思考权拿回来，你失去的不只是手速，是判断力。

## 四、给还在纠结的同学：一个可带走的清单

如果你是在校生或刚入行，别被"我是不是不会写代码了"吓住。把训练目标换一下：

1. **代码能少写就少写**，把 AI 当主力工具，这没问题。

1. **每接到一个需求，先问三句**：这需求服务哪个业务？数据从哪来到哪去？出错了谁最先发现、谁最受影响？

1. **拿到 AI 生成的代码，做一遍"边界体检"**：参数为空会怎样？会不会循环调接口/查库？异常路径覆盖了吗？

1. **保留一条底线能力**：脱离 AI，能独立把一个最小系统从需求写到上线。这是你的安全绳。

1. **把"看懂旧系统 + 对接外部"当成真功夫练**，而不是只练语法和框架。

一句话总结我这两段经历：**写代码是最廉价、也最不稀缺的事；知道"为什么写、为谁写、写错了谁扛"，才是 agent 时代越来越贵的事。**

## 最后

你踩过最离谱的"代码写对了、但业务理解错了"的坑是什么？或者，你现在用 agent 写代码时，会主动去做边界体检吗？欢迎在评论区聊聊——我也在攒一线案例，你的经历可能就是下一篇的素材。
